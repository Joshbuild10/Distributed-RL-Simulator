2.1 · Decentralised vs centralised datacentre — the serial-latency penalty (Llama-405B, 180d)

The downside of distributed RL is serial step latency: (i) moving weights over the WAN every step — the trainer's gradient all-reduce between its sites and the broadcast to inference — and (ii) the number of inference "waves", set by how much aggregate HBM (concurrency + weight-load bandwidth) a node pools. A centralised datacentre relaxes both — a large NVLink domain fuses GPUs into one fat node (72/node here, the GB200 NVL72 rack) and an intra-DC fabric gives ~terabit links between every node (1,000 Gbps) — vs small 16-GPU islands on 1,000 Mbps internet. Everything else is held at base, so the gap between paired bars is the decentralisation penalty. Best centralised node size: NVL72 uses 5,664 GPUs; swept optimum node=48 -> 5,664 (+0.0% vs best). Primary pair (2n, 2o) at 16× sync: below frontier scale the penalty is the inference-wave/node-size effect (and at small budgets decentralised is actually cheaper: centralised's 2×NVL72 floor is 144 GPUs). At frontier scale it is ~2× the GPUs. In 2o the gap holds at ~2× up to ~105 GPUs, then decentralised saturates at the 1 Gbps broadcast floor (406 s/step) while centralised keeps scaling; the trainer's gradient all-reduce (87 s at 150×) stays under it (see 2t). Companion pair (2p, 2q) at lighter 4× broadcast compression: the broadcast grows 4×, so the wall binds at far smaller budgets (2p) and decentralised compute plateaus lower (2q).

Inference node size sweep (2r, 2s). The decentralised→centralised axis made explicit: GPUs per connected NVLink domain from 16 (small donated islands) through 72 (a GB200 NVL72 rack) to 128, WAN/compression held at the centralised fabric so this isolates the node-size effect. 2r — a bigger domain pools HBM bandwidth, lowers the sequential-decode rollout floor, and raises the compute a full stock can burn ~linearly. 2s — the same node-size axis crossed with the compute-budget ladder: the node size barely matters below ~1e24 (a handful of GPUs either way) and dominates at frontier scale, where 16-GPU islands cost ~1.6–2× the GPUs of a ≥32-GPU node. A hollow bar marks a run that misses 180 days — it is drawn at the GPU count that reaches the fastest achievable wall-clock (the full-stock floor), with that wall-clock in the box, so a missed window still reports what the run would cost and how long it would take.

Trainer placement (2t, 2u). A co-located trainer averages gradients over datacentre fabric for free. A distributed one (128-GPU nodes at separate sites, the default) all-reduces them every step over the 1 Gbps WAN — sent and received, and unlike the broadcast never spread over k steps — so it binds whenever gradients are compressed less than ~2× the broadcast's 16×. At Rahman's 150× (4-bit + top-k with error feedback; Covenant-72B ran 146×) it sits below the broadcast and the two placements coincide; at 16× it halves the ceiling. The MoE (Qwen3-235B-A22B (MoE)) sits an order of magnitude lower either way: both WAN transfers scale with its total parameters, its step compute with its active ones.

Appendix · Monte-Carlo predictive intervals (chart 1a whiskers)

n=8,000 draws/anchor, seeded so the page is reproducible. Priors: trainer MFU ~ per-config Triangular whose mode is each preset's own data-grounded trainer MFU (= 0.85× the Ultra-Scale Playbook / huggingface-nanotron node-matched RL-realistic best MFU; 0.85 corroborated independently by prime-rl and AReaL-7B) — so the deterministic "point" and the prior mode are the same number, and the point already reflects the calibrated MFU rather than a flat 0.40. Anchored on nanotron, not the step-time-implied MFU (which would be circular), so it sits above the implied MFU for high-shard anchors and the gap is the FSDP residual. Inference MFU ~ U(0.1, 0.4), sampled independently (physically they correlate, so this errs wide — the conservative direction). E[R] ~ Triangular ±30% about the measured value (a simple "the proxy measurement could be this far off the run's true E[R]" band; prime-rl pinned, its E[R] inverse-solved from its own throughput). Within-run length spread already enters the model exactly via E[R²]=E[R]²(1+cv²) (full second moment, tail included — not a 1-SD slice), so it is not resampled. "explained?" = does the published step time fall inside the 90% interval, i.e. can input uncertainty alone account for the gap? A p95/p5 of ~1.00 means the anchor is broadcast-bound: its step time is set by weight volume and link speed, which neither MFU nor E[R] touches.

Appendix · Node/site caps by GPU family

Two independent physical caps on how a site can be built. Export node cap (BIS CCC): GPUs/node so the node stays under 16 H100-equivalents of both TPP (compute = flops×16 bit) and HBM (1,280 GB) — whichever binds; this is the node size used in chart 2f. Power envelope: GPUs a site can run under a 1 MW / 5 MW facility draw (floor(MW / (board W × 1.6)), i.e. power at the meter including host/NIC/conversion/cooling) — a detectability-tier / site cap on total GPUs, separate from the node cap. The Cerebras CS-4 row (per WSE-3 wafer; a rack = 3 wafers) is included to contrast a wafer-scale part against the cap regime — see the caveats below it.
