2.1 · Decentralised vs centralised datacentre — the serial-latency penalty (Llama-405B, 180d)

The downside of distributed RL is serial step latency: (i) broadcasting fresh weights trainer→inference over the WAN, and (ii) the number of inference "waves", set by how much aggregate HBM (concurrency + weight-load bandwidth) a node pools. A centralised datacentre relaxes both — a large NVLink domain fuses GPUs into one fat node (72/node here, the GB200 NVL72 rack) and an intra-DC fabric gives ~terabit trainer→inference links (1,000 Gbps) — vs small 16-GPU islands on 1,000 Mbps internet. Everything else is held at base, so the gap between paired bars is the decentralisation penalty. Best centralised node size: NVL72 uses 5,664 GPUs; swept optimum node=48 -> 5,664 (+0.0% vs best). Primary pair (2n, 2o) at 16× sync: the broadcast is small enough that the WAN is inert, so the penalty is purely the inference-wave/node-size effect — ~2× the GPUs at frontier scale (though at small budgets decentralised is actually cheaper: centralised's 2×NVL72 floor is 144 GPUs). Companion pair (2p, 2q) at lighter 4× sync: the broadcast term grows 4× and the 1 Gbps decentralised link becomes binding — decentralised flips from wave- to broadcast-bound (2p) and its achievable compute plateaus as the broadcast wall caps it, while centralised (terabit) keeps scaling (2q).

Inference node size sweep (2r, 2s). The decentralised→centralised axis made explicit: GPUs per connected NVLink domain from 16 (small donated islands) through 72 (a GB200 NVL72 rack) to 128, WAN/compression held at the centralised fabric so this isolates the node-size effect. 2r — a bigger domain pools HBM bandwidth, lowers the sequential-decode rollout floor, and raises the compute a full stock can burn ~linearly. 2s — for a fixed Grok-3-scale run the cost is U-shaped: 16-GPU islands are rollout-bound (~2× the GPUs), ≥32 flips to update-bound and flattens, creeping back up past ~72 as coarse node granularity wastes GPUs.

Appendix · Monte-Carlo predictive intervals (chart 1a whiskers)

n=8,000 draws/anchor, seeded so the page is reproducible. Priors: trainer MFU ~ per-config Triangular whose mode is each preset's own data-grounded trainer MFU (= 0.85× the Ultra-Scale Playbook / huggingface-nanotron node-matched RL-realistic best MFU; 0.85 corroborated independently by prime-rl and AReaL-7B) — so the deterministic "point" and the prior mode are the same number, and the point already reflects the calibrated MFU rather than a flat 0.40. Anchored on nanotron, not the step-time-implied MFU (which would be circular), so it sits above the implied MFU for high-shard anchors and the gap is the FSDP residual. Inference MFU ~ U(0.1, 0.4), sampled independently (physically they correlate, so this errs wide — the conservative direction). E[R] ~ Triangular ±30% about the measured value (a simple "the proxy measurement could be this far off the run's true E[R]" band; prime-rl pinned, its E[R] inverse-solved from its own throughput). Within-run length spread already enters the model exactly via E[R²]=E[R]²(1+cv²) (full second moment, tail included — not a 1-SD slice), so it is not resampled. "explained?" = does the published step time fall inside the 90% interval, i.e. can input uncertainty alone account for the gap? A p95/p5 of ~1.00 means the anchor is broadcast-bound: its step time is set by weight volume and link speed, which neither MFU nor E[R] touches.

Appendix · Node/site caps by GPU family

Two independent physical caps on how a site can be built. Export node cap (BIS CCC): GPUs/node so the node stays under 16 H100-equivalents of both TPP (compute = flops×16 bit) and HBM (1,280 GB) — whichever binds; this is the node size used in chart 2f. Power envelope: GPUs a site can run under a 1 MW / 5 MW draw (floor(MW / board W)) — a detectability-tier / site cap on total GPUs, separate from the node cap. The Cerebras CS-4 row (per WSE-3 wafer; a rack = 3 wafers) is included to contrast a wafer-scale part against the cap regime — see the caveats below it.
